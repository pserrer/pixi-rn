title: Haptics
description: Fail-soft vibration feedback, in its own package, on Android's media channel.
---

Haptics live in a **separate package**, `@pixi-rn/haptics`. It does not depend on
`pixi-rn` and `pixi-rn` does not depend on it — install it if you want haptics,
skip it and nothing about the renderer changes.

```sh
npm install @pixi-rn/haptics
npx expo install expo-haptics
```

```tsx
import { impactAsync } from '@pixi-rn/haptics';

// `enabled` is the user's own setting — pass it through on every call rather
// than caching it, so a settings toggle takes effect immediately.
impactAsync(settings.vibration, 'heavy');
```

Haptics are an enhancement, never a dependency. A device with no vibrator, a
simulator, or a user who has turned system haptics off must all behave as if the
calls simply did nothing — so every function swallows its own failures. No call
site needs a `try`/`catch`, and none of them returns a promise you have to
handle.

<Callout type="warn" title="It is native code">
  Autolinking is **install-level**: installing this package compiles its Android native side into your build whether or
  not you import it. So it needs a development or EAS build, it cannot run in Expo Go, and it cannot reach a device over
  OTA. That is exactly why it is not part of `pixi-rn` — no import boundary can contain a native dependency, only a
  package boundary can, so `pixi-rn` stays Expo Go friendly for everyone who doesn't want this.
</Callout>

## The three cues

```tsx
import { impactAsync, selectionAsync, notificationAsync } from '@pixi-rn/haptics';

impactAsync(enabled, 'medium'); // a collision, a landing, a snap into place
selectionAsync(enabled); // a picker stepping, a slider passing a detent
notificationAsync(enabled, 'success'); // a purchase clearing, an action rejected
```

The first argument is always the **user's own on/off setting**. Passing it per
call rather than configuring it once is deliberate: a settings toggle then takes
effect immediately, with nothing to re-wire and no stale copy to invalidate.

`impactAsync` takes `'light' | 'medium' | 'heavy' | 'rigid' | 'soft'` (default
`'medium'`), mapped onto `expo-haptics`' own `ImpactFeedbackStyle`.
`notificationAsync` takes `'success' | 'warning' | 'error'` (default
`'success'`).

All three are **fire-and-forget**. They are typically called from a frame loop's
event handling, where awaiting a native round-trip would sit between the
simulation step and the render; and a rejection (no vibrator, permission
withheld) must never surface as an unhandled promise rejection.

## Why this attaches `USAGE_MEDIA`

Android's system _haptic feedback_ level — a setting about UI touches, separate
from its media-vibration level — silences every other JS-reachable way to
vibrate the phone:

| approach                                                   | amplitude          | suppressed by the haptic-feedback level |
| ---------------------------------------------------------- | ------------------ | --------------------------------------- |
| `expo-haptics`' cross-platform cues (`Vibrator` waveforms) | ≤ 70/255 (~27%)    | **yes** (no usage attributes)           |
| `performAndroidHapticsAsync` (the haptic engine)           | the platform's own | **yes** (gated outright)                |
| `Vibration.vibrate` (React Native core)                    | full               | **yes** (no usage attributes)           |

None of them report a failure when suppressed — a call simply produces no
vibration, indistinguishable from a device with no vibrator. This package's
native side attaches `AudioAttributes.USAGE_MEDIA` instead, which the
haptic-feedback level does not gate.

<Callout type="warn">
  This lets your app vibrate while the user has touch feedback switched off. Only ship it if you give the player their
  own vibration toggle — every function takes that flag as its first argument, and you must pass it honestly.
</Callout>

## What runs where

`impactAsync` and friends pick a backend at runtime, so one call site covers
every platform:

| where                             | what runs                           | follows the system setting   |
| --------------------------------- | ----------------------------------- | ---------------------------- |
| Android, native side compiled in  | the media channel                   | no                           |
| Android, Expo Go / offline export | `Vibration.vibrate`, full amplitude | yes                          |
| iOS                               | `expo-haptics` impact generators    | n/a — no equivalent trapdoor |

The native module is resolved with `requireOptionalNativeModule`, so the
fallbacks are automatic rather than something you configure.

## The raw vibrator

For direct control over duration and amplitude, the native handle is exported
too:

```tsx
import { PixiRnMediaVibration } from '@pixi-rn/haptics';

PixiRnMediaVibration?.vibrate(45, 255); // 45ms at full amplitude (1..255)
PixiRnMediaVibration?.vibratePattern([0, 25, 90, 25]); // [wait, buzz, …] ms
```

⚠️ It is **`null`** on iOS, in Expo Go, and in any build without the native side
— hence the `?.`. This is easy to miss, because it is never null on the platform
you develop the feature on.

## Diagnostics

`hapticsDiagnostics()` reports the platform, which backend is in use, how many
cues have been requested, and the last error — useful when haptics "don't work"
and you need to separate "the app never asked" from "the app asked and something
threw".

⚠️ Its `lastError: null` means **nothing threw**. It does not mean the device
buzzed; no platform reports that back.
