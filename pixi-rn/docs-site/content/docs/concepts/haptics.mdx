title: Haptics
description: Fail-soft vibration feedback, behind its own entry point.

Haptics are an enhancement, never a dependency. A device with no vibrator, a
simulator, or a user who has turned system haptics off must all behave as if the
calls simply did nothing — so every function here swallows its own failures. No
call site needs a `try`/`catch`, and none of them returns a promise you have to
handle.

```tsx
import { impactAsync } from 'pixi-rn/haptics';

// `enabled` is the user's own setting — pass it through on every call rather
// than caching it, so a settings toggle takes effect immediately.
impactAsync(settings.vibration, 'heavy');
```

## The three cues

```tsx
import { impactAsync, selectionAsync, notificationAsync } from 'pixi-rn/haptics';

impactAsync(enabled, 'medium'); // a collision, a landing, a snap into place
selectionAsync(enabled); // a picker stepping, a slider passing a detent
notificationAsync(enabled, 'success'); // a purchase clearing, an action rejected
```

The first argument is always the **user's own on/off setting**. Passing it per
call rather than configuring it once is deliberate: a settings toggle then takes
effect immediately, with nothing to re-wire and no stale copy to invalidate.

`impactAsync` takes `'light' | 'medium' | 'heavy' | 'rigid' | 'soft'` (default
`'medium'`), mapped onto `expo-haptics`' own `ImpactFeedbackStyle`.
`notificationAsync` takes `'success' | 'warning' | 'error'` (default
`'success'`).

All three are **fire-and-forget**. They are typically called from a frame loop's
event handling, where awaiting a native round-trip would sit between the
simulation step and the render; and a rejection (no vibrator, permission
withheld) must never surface as an unhandled promise rejection.

## Android drives the vibrator directly

There are three ways to make an Android phone buzz from JS, and **all three are
silenced by the same system setting**:

| approach                                                   | amplitude          | suppressed by the haptic-feedback level |
| ---------------------------------------------------------- | ------------------ | --------------------------------------- |
| `expo-haptics`' cross-platform cues (`Vibrator` waveforms) | ≤ 70/255 (~27%)    | **yes** (no usage attributes)           |
| `performAndroidHapticsAsync` (the haptic engine)           | the platform's own | **yes** (gated outright)                |
| `Vibration.vibrate` (React Native core)                    | full               | **yes** (no usage attributes)           |

The engine feels best, and it is what this module used in `0.8.0`. It has a
trapdoor: when the system's haptic-feedback level is **0**, it does nothing —
and says nothing. `View.performHapticFeedback` returns a boolean reporting
whether it performed, `expo-haptics` discards that boolean, so the call resolves
successfully having produced no vibration at all. Nothing observable from inside
the app distinguishes that from a device with no vibrator.

So on Android this module calls `Vibration.vibrate` with per-cue durations: of
the three it is the strongest when haptics are enabled, running the motor at
full amplitude rather than a quarter of it. iOS keeps `expo-haptics`, where the
impact generators are the right thing and have no equivalent trapdoor.

<Callout type="warn" title="None of these escapes the system setting">
  All three are silenced when the system's haptic-feedback level is 0 — verified on a device, where every one of them is
  inaudible and none reports anything wrong. This module picks `Vibration.vibrate` because it is the strongest of the
  three when haptics *are* enabled, not because it bypasses anything. An earlier version of this page claimed it did;
  that was wrong.

Bypassing the setting needs **native code** — see below. That is deliberately out of scope for this package: shipping
native code would cost every consumer their Expo Go workflow (autolinking is install-level, so no import boundary can
contain it), and overriding a user's stated OS preference is a decision only an app — one with its own vibration
toggle — has standing to make.

</Callout>

## If you need it regardless of the system setting

Install the companion package:

```sh
npm install @pixi-rn/haptics
```

That is the entire integration. Every cue above then vibrates on Android's
**media** channel, which the haptic-feedback level does not touch — no import,
no registration, no change at any call site. **Verified on a device with haptic
feedback set to 0: cues buzz, where all three JS paths are silent.**

It works by native-module _name_ lookup at runtime, so this package takes no
dependency on it: with the companion absent, the same calls fall back to the
portable path and follow the system setting as before.

<Callout type="warn" title="Why a package and not a subpath">
  Autolinking is **install-level**. Native code inside `pixi-rn` would be compiled into every consumer's build whether
  or not they imported it, costing everyone their Expo Go workflow — no import boundary can prevent that, but a package
  boundary can. It also means installing the companion requires a development or EAS build, and it cannot reach a device
  over OTA.
</Callout>

<Callout type="warn">
  Installing it lets your app vibrate while the user has touch feedback switched off. Only do it if you give the player
  their own vibration toggle — every function here takes that flag as its first argument, and you must pass it honestly.
</Callout>

## Installation

Haptics live behind their own entry point, `pixi-rn/haptics` — the same rule
[`audio`](/docs/concepts/audio) follows, so a native capability never rides
along in the root barrel for consumers who don't use it. Install `expo-haptics`
alongside it:

```sh
npx expo install expo-haptics
```

It is a native module, so adding it needs a fresh native build; an OTA update
onto a binary without it will not gain haptics.

<Callout title="Why there is no setup call">
  Earlier versions had the host inject `expo-haptics` with a `setHapticsModule` call, so that naming the package here
  couldn't force it on every consumer — a bundler resolves imports statically, so an import in the root barrel is an
  import for everybody. Moving the module behind its own entry point solves that directly and better: the dependency now
  follows the feature. Injection was left buying only stubbability, while charging a real price — a host that forgot the
  registration call got silence, with nothing failing to say so. A plain import has no step to forget.
</Callout>
